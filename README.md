# cs-project-template

The shared files of every cscosine repository, as a [Copier](https://copier.readthedocs.io) template
(`PLAN-cscosine-org.md`, S3: the base layer). One template, as few differences between repositories as possible: the
answer `kind` only decides the Python layout, the csorchestrator switch of the setup scripts and which files a
repository gets.

| `kind` | What it is | Python | Gets |
|---|---|---|---|
| `tool` | Python package with its own CI (csCMake, csorchestrator, csWiki) | `src/` layout | everything, plus `.github/workflows/ci.yml` (its minimum-versions job runs the tests with the lower bounds of the runtime dependencies) |
| `project` | csorchestrator recipe, with or without C++ sources of its own (the distributions and the applications) | flat: the recipe at the root | everything, `setup.sh` with the csorchestrator switch; its CI is generated by csorchestrator |
| `library` | first-party C++, built by the project that consumes it, no CI | none | the formatting, checks, git and agent files; no setup, no Python files |

Everything else is the same for every kind: C++ formatting (clang-format only touches C++ and JSON files), CMake
formatting for a `project` and a `library` (gersemi, `.gersemirc`: the hook installs the signatures of the csCMake
commands from the csCMake tag of the template, `gersemi-cscmake`; a `tool` has its own or no CMake), the Python
hooks (they skip a repository without Python files), the csorchestrator workspace ignored (the answer `workspace_dir`
of a `project`, default `workspace`), the pytest options (`--run-all`, as CI; `--run=<marker>`). The opt-in markers
themselves (slow, git, smoke, …) are declared by a project in its own `tests/conftest.py` (see `template/conftest.py`).

## Use

Copier: in a repository it comes with the dev tools (`./setup.sh`, then `source .venv/bin/activate`). To create a
new repository, once per machine (Python 3.9 or newer; any of these):

```bash
pipx install copier
uv tool install copier
python3 -m pip install --user copier
```

### Create a new repository

```bash
cd ~/myWorkspace                                           # the folder holding the clones
copier copy gh:cscosine/cs-project-template csNewProject   # asks name, description, kind, ...
cd csNewProject
git init -b main
./setup.sh                                                 # library: pre-commit install instead
source .venv/bin/activate                                  # the hooks (mypy) run in the venv
git add -A
git update-index --chmod=+x setup.sh open-code.sh          # needed on Windows (no executable bit); not for a library
git commit -m "Create from cs-project-template"
gh repo create cscosine/csNewProject --public --source . --push
```

Copier takes the latest tag of the template; another one: `--vcs-ref v0.1.0`.

Then register the repository in [`cscosine/.github`](https://github.com/cscosine/.github): one line, and the
organisation knows it from then on. In `scripts/`:

| Add | What it gives |
|---|---|
| The name under its kind in `github-settings.json` (`"tool"`, `"distribution"`, `"application"`, `"library"`, …) | `github_settings.py --apply <name>`: the rulesets (no force push or deletion of `main`, stable tags immutable), merge settings, release-note labels. And its **status is tracked**: the nightly `ecosystem` workflow lists it in `ECOSYSTEM.md` with its kind, latest release and rc, CI state of `main`, template version, and flags drift (behind the template, old pins) |
| A line in `ecosystem.json` (public repositories worth showing: its group and one sentence) | Its card on the public organisation page (`profile/README.md`): description, latest release, CI badge, place in the release-chain graph |

A repository that is in neither file exists on GitHub but is invisible to the overview and unprotected.

### Update a repository to a new template version

Which version a repository is on: `.copier-answers.yml` (`_commit`); `copier check-update` says whether a newer one
exists. For every repository at once: the "Project template" section of `cscosine/.github` `ECOSYSTEM.md` (nightly).

In the repository, clean working tree, venv active (`source .venv/bin/activate`), on a feature branch:

```bash
git switch -c feature/template-update
copier update --defaults            # to the latest tag, same answers; another tag: --vcs-ref vX.Y.Z
git status                          # review; conflicts are inline (<<<<<<< before / >>>>>>> after), resolve them
pre-commit run --all-files && pytest --run-all
git add -A && git commit -m "Update to cs-project-template vX.Y.Z"
```

A large file to add on purpose (a dataset): in `.pre-commit-config.yaml`, under `check-added-large-files`, the
lines between its `project: begin` / `project: end` markers are the project's: uncomment the `exclude` and set the
paths.

Files no hook may touch (the upstream files of a library copied from elsewhere, kept as they are): in
`.pre-commit-config.yaml`, the top-level `exclude:` between the first `project: begin` / `project: end` markers (a
regex on the path). For C++ formatting only, a `.clang-format` with `DisableFormat: true` in a folder (clang-format
takes the nearest one) leaves the C++ files under it unformatted while the other hooks still run.

Change an answer at the same time: `copier update --defaults --data workspace_dir=ws` (or without `--defaults`, to be
asked every question again). Copier replays the project's own changes onto the new template version (a three-way
merge), so the project lines (below) are kept; a template-owned line edited in the repository conflicts.

### Adopt the template in an existing repository

On a feature branch: `copier copy --overwrite gh:cscosine/cs-project-template .`, then put back what is the project's
(the project tables of `pyproject.toml`, its pre-commit hooks between the `project: begin` / `project: end` markers, its README outside
the template block), review the diff, commit. From then on: `copier update`.

## Who owns which file

One owner per file. A template-owned file is never edited in a repository: change it here, tag, `copier update`.

| Owner | Files |
|---|---|
| Template | `setup.sh` / `setup.ps1`, `open-code.*`, `conftest.py`, `.clang-format`, `.vscode/settings.json`, `.vscode/extensions.json`, `.gersemirc` (projects, libraries), `.github/` (`pull_request_template.md`, `release.yml`, `actionlint.yaml`, `workflows/ci.yml` of the tools), `CLAUDE.md`, `.claude/cscosine-rules.md`, `.claude/settings.json`, `LICENSE` |
| Template, with a project part | `.pre-commit-config.yaml`: the project's hooks go between the `project: begin` and `project: end` markers, before the template's final check; `.gitattributes`, `.gitignore`: the project's lines go after the `--- project ---` marker at the end |
| Mixed | `pyproject.toml`: `[project]` and the tables after `--- project ---` (coverage, import-linter, …) are the project's; `[build-system]` and the tables between the `template` markers are the template's. `README.md` and `AGENTS.md`: the block between `<!-- cs-template:begin -->` and `<!-- cs-template:end -->` (getting started, generated files; the agents' entry point and the list of template-owned files) is the template's, the rest the project's |
| Template, created once, then the project's | With a new repository only (never added by an update): the `tests/` skeleton (`tests/<name>/test_placeholder.py`) and, for a tool, the package skeleton `src/<name>/__init__.py` |
| Project | `tests/conftest.py` (when needed): its opt-in markers, its own options and fixtures |
| Others (not the template) | csorchestrator: `<name>_project.py`, `<name>_config.py`, the generated workflow, `csorchestratorsdk/`, `dependencies/`; csCMake: `CMakePresets.json`, `csCMakeProjectSetup.json` |

Agents: `CLAUDE.md` only imports `.claude/cscosine-rules.md` (the rules of every repository) and `AGENTS.md` (what
is specific to the repository, read by every agent tool).

Generated README sections: the same marker convention (`<!-- <owner>:begin -->` … `<!-- <owner>:end -->`) is meant for
blocks written by a tool, e.g. a releases / variants / dependencies block that csorchestrator fills from the recipe
(a pre-commit hook, like the TOC of csWiki).

## csorchestrator switch (`project`)

`./setup.sh` installs the pinned version (the answer `csorchestrator_version`); `--csorchestrator=<tag or branch>`
another one from GitHub; `--csorchestrator=<path>` a local clone, editable (Windows: `-CsOrchestrator`).

## Developing the template

The CI (`.github/workflows/ci.yml`, on every PR, push to `main` and tag) creates a project of every kind from the
commit under test with a hello world (`tests/create_project.py`), then runs in it what a developer runs: the setup
script (`setup.sh`, `setup.ps1` on Windows; for a `project` it installs the pinned csorchestrator), pre-commit on
every file (nothing may change: what the template renders is already formatted) and `pytest --run-all` (the hello
world, csorchestrator importable, an opt-in marker run and a manual one skipped). Tool and project on Linux, macOS and
Windows; library on Linux.

The same by hand, before a PR:

```bash
python tests/create_project.py project /tmp/hello    # tool, project or library; uncommitted changes included
cd /tmp/hello && ./setup.sh && source .venv/bin/activate && pre-commit run --all-files && pytest --run-all
```

Changing the template: PR, CI green, merge, tag `vX.Y.Z`; the repositories move with `copier update` (above).
